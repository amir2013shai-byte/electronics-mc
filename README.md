# Electronics — учебная электроника для Minecraft 1.21.11 (Spigot)

[![build](https://github.com/amir2013shai-byte/electronics-mc/actions/workflows/build.yml/badge.svg)](https://github.com/amir2013shai-byte/electronics-mc/actions/workflows/build.yml)

Плагин + ресурспак, которые добавляют в игру **работающие** электронные компоненты:
светодиоды, диоды, резисторы, конденсаторы, транзисторы, логические вентили,
блоки питания, измерительные приборы и «пустую схему» для сборки цепей.

Цепи считаются по-настоящему (Modified Nodal Analysis), а не «красной пылью»:
`U`, `I`, `P`, заряд конденсаторов, яркость LED'а, сгорание при перегрузке.

| | |
|---|---|
| Игра | Minecraft Java **1.21.11** («Mounts of Mayhem») |
| Ядро сервера | **Spigot / Paper 1.21.11-R0.2** (тестировалось на Paper 1.21.11 build 132) |
| Java | 21 |
| Формат ресурспака | **64 … 75**: `pack_format` 64 + `min_format`/`max_format` 64/75 |
| Формат датапака (рецепты) | **80 … 94**: `pack_format` 80 + `min_format`/`max_format` 80/94 |
| Клиентские моды | **не требуются** |
| Компонентов | 114 видов (69 спаечных деталей + рудная цепочка и сплавы, микроконтроллер, платы, приборы, 4 станка, 9 деталей привода, рукоять и водяное колесо, машинный генератор, свинцовый аккумулятор) |
| Состояний модели в ресурспаке | **3390** (565 визуальных состояний × 6 ориентаций) |

## 1. Как выполнена идея «модификации игрока» (800+ состояний)

Техника «изменить игрока, чтобы он отдавал новые блоки без клиента» требует
записи в состояние сущности игрока. Проверено по API Spigot 1.21.11:

* у `org.bukkit.entity.Player` **нет** канала записи NBT/`updateNbt` — state-API
  игрока в Spigot не открыт (полностью доступен только через NMS-рефлекс,
  который ломается на каждой версии и не проходит по «без модов» на стороне
  клиента);
* у `Block` нет `PersistentDataContainer` — состояние блока нельзя хранить
  ванильными средствами;
* `Player#sendActionBar(String)` в этом API тоже нет (есть только Adventure-версия).

Поэтому «800+ изменяемых состояний» реализованы там, где их **действительно
видит клиент без модов** — в реестре состояний модели ресурспака, которым
управляет сервер:

1. **3390 определений состояния модели.** Для каждой пары
   *(компонент, визуальное состояние, ориентация)* в ресурспаке есть свой
   `assets/electronics/items/<id>_<state>.json`, выбираемый сервером через
   компонент предмета `minecraft:item_model`. Индекс состояния адресует и
   `custom_model_data` (там же `minecraft:range_dispatch`), так что модель
   переключается одним числом — ровно как «запись в состояние».
2. **Ориентация** (`Orientation`: north/east/south/west/up/down) и
   **состояние** (`off / dim / on / burnt / reverse / closed`) хранятся на
   сервере в реестре плагина и толкаются клиенту при каждом рендере —
   6 × 565 = 3390 адреса, что и покрывает «800+».
3. **Визуал в мире** — `ItemDisplay`/`TextDisplay` (сущности-дисплеи есть в
   1.21 и не требуют клиента): модель компонента парит над платой, подпись
   прибора показывает вольты/амперы прямо над деталью.
4. Если нужен именно «чистый» способ без дисплеев — `render.mode: none`
   (тогда всё видно по предмету в руке и по блок-модели платы, перекрашенной
   ресурспаком).

> Итог: обещанный эффект «сотни переключаемых состояний без клиентского мода»
> достигнут, но не через NBT игрока (в Spigot это невозможно без NMS), а через
> серверно-управляемый реестр состояний модели. Это единственный переносимый
> способ на чистом Spigot API.

## 2. Установка

```
1) Плагин
   cp plugin/target/Electronics-*.jar /plugins/     # имя = версия плагина
   # или собрать: cd plugin && mvn -DskipTests package

2) Ресурспак (выдаётся игрокам, если resource-pack.auto-apply: true)
   release/electronics-resourcepack.zip  ->  в resource-pack.url
   либо руками: .minecraft/resourcepacks/ + Apply in settings

3) Рецепты (по желанию, если не хочется держать крафты на сервере)
   release/electronics-recipes-datapack.zip -> /plugins/Electronics/world_datapacks
   (или просто в /world/datapacks/)

   build/*.zip — то же самое, но промежуточный результат tools/publish.sh;
   в репозитории не лежит, в инструкции смотреть надо на release/.
```

Плагин при первом старте создаёт:

```
plugins/Electronics/config.yml            — настройки (см. docs/config.md)
plugins/Electronics/labs/*.yml            — 3 практические работы (примеры)
plugins/Electronics/builds/*.json         — готовые учебные сборки
plugins/Electronics/registry.json         — реестр компонентов (аналог PDC)
```

## 3. Чему учат и что можно собрать

**Компоненты:** 114 видов — 8 номиналов резисторов + фоторезистор, NTC и
измерительный шунт (11 всего), 4 конденсатора, 5 LED'ов + лампа, обычный диод и
Шоттки, 2 биполярных транзистора, 5 вентилей (AND/OR/XOR/NOT/компаратор),
7 источников (AA 1.5 В, «таблетка» 3 В, «крона» 9 В, лабораторный БП 0..12 В,
синус, воздушно-цинковый, приводной 220 В) + солнечная панель и генератор,
шина земли, 7 проводов (4 цвета + голый, лужёный, эмальпровод), макетная плата,
кнопка, 2 ключа, потенциометр, зуммер, 2 мотора (12 В и 220 В приводной),
вольтметр, амперметр, мультиметр, осциллограф, кусачки, пробник, «пустая схема» и
«рабочий стол», а с v1.2.0 — полный тракт питания: плавкие вставки,
PTC-самовосстанавливающийся, варистор, диодный мост, полярный электролит,
7805/7812/LM317, трансформаторы 230→12 В и 230→9 В и оплётка для выпайки.
Вставок сейчас пять (100 мА, 1 А, 5 А, 2 А медленный, 10 А медленный): три из
них — v1.2.0, а `fuse_slow_10a` на 10 А привёл v1.4.0 вместе с приводом.
С v1.3.0 добавился верх цепи — откуда ток вообще берётся: рудная цепочка
(жилы в породах, геозонд, куски руды, плавка слитков, зачистка и лужение
монтажного провода) и микроконтроллер `mcu_atmega328` с программатором,
кварцем 16 МГц и воздушно-цинковым элементом — со своим C-подобным языком.
С v1.3.1 — металлургия (тигельная печь, волочильный стан, бронза/латунь/шлак),
а с v1.4.0 — привод: шесть `kind: KINETIC` деталей, мотор 220 В и его защита
(§4d), а свинцовый аккумулятор умеет помнить заряд (§4e). В `Kind` 46 значений
(44 встречаются в реестре), станков четыре: паяльный
стол, программатор, тигельная печь и волочильный стан.

**Осциллограф (v1.5.0)** — у приборов наконец появился график. Ставится как
обычная двухвыводная деталь, вход — 10 МОм (`internal_resistance`): цепь он не
нагружает, потому что осциллограф — это вольтметр с памятью. Над блоком висит
`TextDisplay` с растром 40×16 точек: знак Брайля — 2×4 пикселя, значит строка
экрана — 20 знаков, всего 4 строки. Никаких модов на клиенте: сетку, трассу и
послесвечение считает сервер. `ПкМ` по прибору переключает развёртку
(×1/×2/×4/×8; на минимальной экран = 2 с при шаге 50 мс). Триггер — по
восходящему фронту, поэтому картинка не ползёт, а вертикальный масштаб
подбирается сам (запас 30 %). Подпись под блоком: `pk-pk 12.0 В · 1.2 В/дел ·
1.00 Гц · 0.20 с/дел`. Настройки — `scope.text-size`, `scope.refresh-ticks`,
`scope.afterglow` (прошлый кадр дорисовывается через каждый третий столбец, так
редкий импульс не исчезает между обновлениями).

**Питание и защита (v1.2.0)** — что физически считается:

| Деталь | Модель | Что видно в цепи |
|---|---|---|
| `fuse_cartridge_1a` / `_5a` / `fuse_slow_2a` | накопленный `∫I²dt` против `blow_i2t` | 800 мА через 1-амперную вставку живёт вечно, коротыш выбивает её за один шаг, и нагрузка гаснет (`PASS предохранитель I²t`) |
| `ptc_500ma` | R = R0·(1+0.4 %/°C) до `trip_temp`, дальше +порядок на 2.5 °C; тепло — `heat_j`, отвод — `thermal_k` | держит 743 мА без нагрева; коротыш за 30 шагов греет корпус до ~95 °C и обрезает ток в разы, потом деталь остывает и включает цепь сама — менять её не нужно |
| `mov_275v` | I = K·U^α, α = 9 | при 9 В течёт 9 нА (замер selftest), при 390 В деталь — короткое замыкание; 3 поглощённых импульса = деградация в открытый ключ |
| `bridge_kbu8` | 4 p-n перехода в корпусе | двухполупериодное выпрямление с падением ~1.1 В; в редакторе ставится крестом в средний ряд |
| `shottky_sbr30` | тот же переход, `v_drop` 0.35 В | свободный диод на 3 А: меньше греться, быстрее, ставится обратно-параллельно катушкам |
| `cap_elec_2200uf` | обычный C/dt + утечка 8 МОм + `polar` | переплюсовка -> состояние `rev`, дым и отказ до перепайки; плюс сажает напряжение в тепло |
| `reg_7805` / `reg_7812` / `reg_lm317` | Uвых = min(Uцель, Uвх − dropout), Norton 1/rz; при отдаче выше `i_limit` — режим источника тока | 4.99 В на 330 Ом, 1.06 В при 3 В на входе (dropout), коротыш = 1.01 А, а не 8 А (`PASS 7805`) |
| `xfmr_230_12` / `_230_9` | две связанные индуктивности, обратный Эйлер, M = k·sqrt(L1·L2) | постоянку не передаёт (0 А), на 50 Гц U1/U2 = 19.27 против 19.17 по виткам — 0.5 % (офлайн-тест `tools/TestCoupled.java`) |
| `source_ac` | ЭДС = U·sin(2π·t/T), фаза — общий счётчик шагов симуляции | узел меняет знак каждый полупериод (`PASS синус меняет полярность`); шаг 50 мс не размещает 50 Гц (Никвист 10 Гц), поэтому в реестре 1 Гц |
| `desolder_braid` | расходник без электричества | снимает припой: сгоревшую деталь можно выпаять обратно в инвентарь, а не выбросить |

**Отказ — не потеря предмета.** Перегруженная деталь уходит в состояние `burnt`
(3-е визуальное состояние) и остаётся в мире: её чинят на месте — паяльный стол
не дальше 5 блоков, прогретое жало, оплётка ×1 и припой ×1 (`/elec repair` без
права `electronics.admin`), либо то же самое бесплатно с правом админа (и
`/elec repair all`). При починке обнуляются накопленный I²t, температура корпуса,
деградация варистора и сам флаг отказа — `Simulation.repair()` делает это одним
вызовом, и selftest проверяет, что I²t после перепайки снова равен нулю.

**Магниты и катушки (8 позиций):** постоянный магнит (1.4 мТл на своей
клетке — рядом с ним замыкается геркон), электромагнит (60 Ом, 20 мГн,
0.9 мТл на ампер), дроссели 10 мГн и 10 Гн, реле 5 В (катушка 120 Ом,
срабатывает от 15 мА, удерживает до 8 мА — гистерезис), геркон (замыкается
при 0.7 мТл), фоторезистор (100 кОм в темноте, сотни Ом на свету) и
NTC-термистор B = 3950 с саморазогревом. Решатель считает поле по клетке
геркона и шести соседям, а катушку — по Norton-модели `g = dt / (L + dt·R)`,
поэтому видно, как ток разгоняется не мгновенно, а за несколько шагов.

**Как собирают цепь**

1. `ПкМ` с «рабочим столом» (`bench`) — ставится блок-плата.
2. `ПкМ` столом с компонентом в руке — компонент встаёт на плату.
3. `Shift+ПкМ` — поворот на 90°; `ПкМ` по детали — смена состояния
   (ключ/кнопка замыкаются, потенциометр подстраивается).
4. Соединение = **пара соседних блоков {A,B}**: контакт детали «смотрит» в
   сторону её ориентации, и у двух деталей, стоящих вплотную лицом к лицу,
   вывод попадает в одну и ту же пару — это один узел. Инертная подставка
   (`bench`) узлы не объединяет, поэтому цепочка на столе не замыкается.
5. **Провод — «крест»** (6 выводов + «нога» вниз): объединяет всё вокруг себя,
   поэтому из проводов делают и «мостик» через зазор, и обратную шину, и
   отвод/перемычку стопкой (провод над проводом). Шина земли и шина питания —
   такие же хабы. Разветвление (подключить вольтметр параллельно) делают так:
   в линию ставят провод-хаб, от него вверх — перемычку-провод, а уже к ней
   прибор.  Предохранитель и «двухполюсники» остаются строго вдоль оси.
6. `ПкМ` пробником/мультиметром по узлу — показать напряжение; над
   приборами висит TextDisplay со значением.

**Что решатель честно умеет**

* закон Ома, последовательные/параллельные цепи, делители;
* кусочно-линейные LED/диод (порог 1.8 В у красного LED, 0.6 В у диода, плюс
  дифференциальное сопротивление 25 Ом);
* лампа накаливания с холодным/горячим сопротивлением и яркостью;
* конденсаторы: шаг интегрирования 50 мс, companion-модель (заряд/разряд по
  экспоненте — видно в `rc_blink`, τ = R·C); полярные следят за
  полярностью и пробоем;
* транзистор как ключ и усилитель (β, насыщение), вентили (нужны `VCC`+`GND`);
* предохранитель: `I²t` копится **только от превышения** (`over = I² − Iном²`),
  поэтому 800 мА через вставку на 1 А живы 30 с, коротыш выбивает её за один
  шаг, а на 45 % бюджета деталь уже показывает `dim` (видеть, что вставка
  «на подходе», — часть обучения);
* пробой диода в обратном направлении, перегрев > 3 × номинальной мощности →
  состояние `burnt` (визуальное состояние 3), запрет «мёртвой» детали
  до `/elec repair`; у мотора перегрузка ещё и копится (§4d) — пусковой ток не
  обязан быть смертью обмотки;
* КЗ источника: ток ограничивается внутренним сопротивлением, показывается
  в амперметре и в подсказке острова.

Готовые сборки (ставятся в точку под прицелом или с консоли):

* `/elec build led_basic` — крона 9 В → 330 Ом → амперметр → красный LED →
  шина земли, обратный путь проводом по соседнему ряду. Проверено на живом
  сервере: `I = 20.19 мА`, `U_LED = 2.31 В`, `b = 1.00` (расчёт
  (9 − 1.8)/(1.2 + 330 + 0.5 + 25) = 20.2 мА), островков — 1.
* `/elec build rc_blink` — БП 12 В → 1 кОм → 1000 мкФ → зелёный LED → шина
  земли, обратный путь проводом. τ = R·C = 1 с: в первый момент
  конденсатор — коротышка, LED горит вполнакала, потом ток убывает по
  экспоненте и LED гаснет. Замерено на сервере (`/elec sim N` шагами):
  t=2 → I=7.98 мА, U_C=1.72 В, b=0.40; +41 тик → 2.94 мА, 6.89 В;
  +104 → 0.42 мА, 9.47 В; +245 → 0.00 мА, 9.90 В, LED `s0`. Теория:
  I₀=(12−1.8)/1025 = 9.9 мА, U_C(∞)=12−2.1=9.9 В ✓. Номиналы подобраны так,
  чтобы резистор не сгорел (0.064 Вт при норме 0.125 Вт); с 220 Ом при 12 В
  решатель честно его сжигает (1.73 Вт) — это тоже учебный кейс.

## 4. Команды

```
/elec give <id|all> [число]        выдать компонент
/elec list [фильтр]                список компонентов (114 id + фильтры по kind)
/elec veins [чанков]               что обещают недра вокруг вас (жила, глубина, сколько осталось)
/electro show [ стр.]              каталог всех предметов плагина в GUI (описание + выдача)
/elec model <id> <сост> <ориент>   какой индекс модели получится (0..3245)
/elec info                         состояние движка: компоненты, острова, мкс
/elec sim [тики]                   пересчитать сейчас
/elec selftest                     22 проверки физики и пака прямо в консоли (config: selftest)
/elec dump [мир] [число]           U/I/P каждой детали (удобно с консоли)
/elec rotate                       повернуть деталь под прицелом
/elec repair [all]                 починить сгоревшие
/elec clear [all]                  убрать детали
/elec mode <display|none>          способ отрисовки
/elec recipe                       рецепт/требования пайки предмета в руке
/elec solder                       открыть паяльный стол руками (урок, отладка)
/elec schematic                    нарисовать/протестировать схему в GUI-редакторе
/elec schematic print|save|check   netlist текущей цепи в мире, сохранение, сверка
/elec build list|<имя>|save <имя>  учебные сборки-пресеты
/elec rig                        что берёт ближайший механизм (обороты, момент, тяга)
/elec rig place [мир x y z]           собрать у учебной лесопилки (консоль — с координатами)
/elec rig undo                       убрать сборку и вернуть блоки как было
/elec reload                       конфиг + реестр компонентов + рецепты

/lab list                          практические работы
/lab show <имя>                    задание + нужные компоненты
/lab check <имя>                   сверка схемы (состав + топология-сигнатура)
/lab save <имя>                    зафиксировать эталон с текущей цепи
/lab start <имя>                   показать задание и выдать материалы
```

Права: `electronics.use` (игрок), `electronics.build`, `electronics.give`,
`electronics.admin`. `electro` — алиас `elec`, так что `/electro show` и
`/elec show` одно и то же.

## 4a. Лист-редактор схемы (`/elec schematic`, ПКМ «Пустой схемой» в руке)

![лист-редактор](docs/editor-mockup.png)
*макет раскладки GUI (не скриншот): слоты 0–15 палитра, 18–44 лист, 45–50 кнопки*

Схема в редакторе — это рисунок, а не постройка: сетка 9×3 в GUI сундука.
Слева сверху — палитра деталей (16 на страницу, ◀ ▶ листают), ниже — лист:
ЛКМ ставит выбранную деталь, ПКМ поворачивает, Shift+ПКМ на ключе замыкает
его, Shift+ПКМ по клетке стирает, «Ластик» выбирает стерание кистью.

Кнопка «Пересчитать» гоняет нарисованное через **тот же решатель**, что
считает блоки в мире (`Simulation.solveVirtual` → те же `collectIsland`,
`stampAll`, `finish`), и вписывает результаты в подсказку каждой детали:
`U`, `I`, `P`, узлы и состояние. У проводов и шины отдельной строкой пишется
**потенциал узла**, а название клетки подкрашивается по нему — сразу видно
«плюс», «минус» и землю.
Рядом кнопка «Симулировать 20 тиков» — она прогоняет цепь на 20 шагов по 50 мс
подряд, не сбрасывая заряды конденсаторов и ток катушек, так что переходный
процесс (разгон дросселя, заряд RC-цепи) видно прямо в GUI. «Поставить в мире» строит нарисованное
реальными блоками туда, куда смотришь (в том числе на стену: блоки ставят
`pedestal`+плату), «Сохранить сборкой» пишет
`plugins/Electronics/builds/schem_<ник>.json` → `/elec build schem_<ник>`.

Правило узлов то же, что в мире: соседние клетки делят узел, провод —
шестиполюсный перекрёсток (объединяет всё вокруг), поэтому угол цепи делают
проводом, а не «жилой» клеткой. Конденсатор в редакторе всегда стартует с
нулевого заряда — это «момент подачи питания».

## 4a-bis. Пайка: особый метод крафта

Паять так паять. 69 из 114 id (все детали с выводами: резисторы,
конденсаторы, LED'ы, диоды, транзисторы, вентили, реле, геркон, катушки,
мотор, зуммер, приборы, ключи, солнечная панель) **не крафтятся в верстаке
вовсе**: `Recipes.register()` их пропускает, а датапак их не содержит —
в логе это видно как
`зарегистрировано рецептов: 41 (пайка: 69 витрин для JEI, пропущено 7, плавка 3)`
(«пропущено 7» — это то, что в верстаке не собирается вовсе: слитки, сплавы,
шлак и эмальпровод; их делают станки).
Проверить список можно в `shared/components.json` → `meta.soldered` (его же
читают и генератор пака, и плагин, так что разойтись не могут).

Нужны три вещи:

| что | как добыть | зачем |
|-----|-----------|-------|
| **паяльный стол** | `P P / PFP / ICI` (доски, печь, железные самородки, медь) | у него можно прогреть жало: рядом обязан быть горячий блок |
| **паяльник** | `  C /  I / S  ` (медное жало, железный стержень, палка) | жало = температура; прочность 64 пайки, шкала износа видна в инвентаре |
| **припой** | 2 железных самородка + кресало | 1 шт. на 2-выводную деталь, 2 шт. на 3…4-выводную |
| **флюс** | светокамень + мёд в банке | обязателен для LED'ов, ламп, диодов, транзисторов, вентилей, реле, геркона, катушек, конденсаторов, мотора, зуммера и приборов |

Как пользоваться:

1. поставить стол (ПКМ по блоку-подставке, как ставятся детали), рядом — печь
   или костёр;
2. прогреть жало: **ПКМ паяльником по горячему блоку** → 100°, дальше жало
   остывает ≈1.2°/с, так что «прогреть» и «спаять» — два разных действия;
3. открыть стол ПКМ по нему (или `/elec solder` — для урока, когда на одного
   проектора смотрят все) и кликнуть по детали: стол сверит заготовку
   (те же ингредиенты, что были бы в верстаке), посчитает припой и флюс,
   проверит температуру и спишет всё сразу;
4. 60°…99° — нормальная пайка; 20°…59° — **холодная пайка**: припой
   сгорает, деталь не получается (заготовки остаются); <20° — отказ;
5. после 64 паянок жало выгорает — паяльник ломается и его нужно спаять заново.

### JEI / REI / EMI: как крафтится каждая деталь

Клиентский мод не нужен: JEI читает тот же список рецептов, который сервер
синхронизирует всем игрокам в `ClientboundUpdateRecipesPacket`. Плагин кладёт
в него **все 114 id**: 41 обычный крафт в верстаке + 69 «витрин» для спаечных
деталей (`recipe_solder_<id>`). Витрина — это `ShapedRecipe` с той же сеткой
заготовок, что требует стол, и с **паяльным столом в свободной клетке**: в JEI
он выглядит как станок в рецепте (а нажми `R` на столе — и он покажет список
всего, что на нём паяется). Собрать витрину руками нельзя:
`Events#onCraftDisplay` отменяет `CraftItemEvent` и объясняет, куда идти:

```
«Резистор 330 Ом» в верстаке не собирается — её паивают: нужен паяльный стол,
прогретое жало, припой и флюс.
Открой стол ПКМ по нему (рядом должна стоять печь/костёр) или /elec solder
```

Температура, число припоя и необходимость флюса написаны в подсказке самого
предмета (`Items#componentItem` → `Soldering#solderHint`) — JEI показывает её
при наведении, потому что подсказка прилетает вместе с результатом рецепта.
Плотные рецепты 3×3 (солнечная панель, AND, XOR, мультиметр) специально
оставлены по 8 позиций: девятая — под стол, иначе месту в сетке не хватило бы
и «станок» в JEI не появился бы.

Что нужно знать про окружение:

* JEI ставить на сервер не надо, это клиентский мод; на сервере — только плагин
  (и датапак с 38 рецептами, если хочешь, чтобы крафты жили в world — его
  кладёшь в `<world>/datapacks/`, а не в `plugins/`).
* Работает и с REI/EMI/FFBI: они тоже читают список рецептов ванилы.
* `world.recipes: false` в конфиге выключает регистрацию целиком — тогда в JEI
  не будет ни крафтов, ни витрин (при `recipes: true` так и есть).
* Проверка на сервере: `/elec selftest` печатает
  `PASS JEI: витрин 68/(нужно 68), … стол в сетке рецептов: 68/68, в менеджере
  рецептов клиента: 110 (41 крафта + 69 витрин)` — то есть все 114 id реально
  видны клиенту, а не только в реестре плагина.

Свой *категория*-вывод (отдельная страница JEI с температурой и полоской прогресса)
возможен только через клиентский аддон — намеренно не делаем: условие задачи —
никаких модов на клиенте.

Правила живят в одной чистой функции `recipes/Soldering.evaluate(...)` — её же
прогоняет `/elec selftest` (`PASS пайка: …`), поэтому GUI и самопроверка
не могут разойтись. `/elec recipe` со спаечной деталью в руке вместо сетки
верстака печатает заготовку, расход и требуемую температуру.

### Могут ли наши `custom_model_data` задеть чужие предметы (пластинка в проигрывателе)?

Нет — и это не «на глаз», а строки `PASS` и падение проверки пака:

* Состояние модели выбирается **компонентом `item_model` на самом стеке**
  (`electronics:<id>_<состояние>`), а не числом `custom_model_data`. Ветка с CMD
  в `Items.applyModel` — аварийный fallback на ядра старше 1.21.4; чтобы она не
  включилась молча, `selftest` следит:
  `PASS модель задаётся компонентом item_model у 114/114 предметов,
  custom_model_data не ставится ни на одном`.
* `custom_model_data` клиент читает внутри **определения того предмета, который
  лежит в руке**. Наши определители — `assets/electronics/items/*.json` (684 шт.:
  114 базовых + по одному на каждый адрес состояния), диспетчер по CMD есть у
  всех 114 базовых (после того как `states: 6` стало общим
  правилом), и ни один ванильный предмет на них не
  ссылается. Адрес состояния без определения клиент тоже «разрешает» — но запасной
  моделью, и в мире деталь выглядит как плита-основа; именно так выглядела
  жалоба «макетные платы и светодиод — зелёные плашки» (см. §4g). В `assets/minecraft/items/` у нас **ноль** файлов: `music_disc_13`,
  `jukebox`, зелья, яйца спавна и прочее остаются ванильными.
* `tools/check_pack_refs.py` теперь падает, если в паке появится хоть один чужой
  файл кроме разрешённых (атлас-источник + три текстуры кварца) — так «случайно
  перекрываемый ванильный предмет» превращается в ошибку сборки, а не в мистический баг.
* Индексы 0…3245 не глобальные: даже в fallback-режиме число висело бы на стеке
  `SMOOTH_QUARTZ_SLAB` или `BRUSH`, а не на пластинке; чужие стеки плагин вообще
  не трогает (`Items.defOf()` на них возвращает `null`).
* Пластинки и проигрыватель в коде не фигурируют: `grep -riE "music_disc|jukebox|RECORD_"`
  по `plugin/` и `tools/` пуст (совпадение по `disc` — форма керамического
  конденсатора). Звук зуммера/геркона идёт через `world.playSound`, а не через
  вставку предмета.

Единственное, что мы по-настоящему перекрываем в чужом namespace —
`quartz_block_side/top/bottom`: гладкий кварц и полублоки во всём мире выглядят
как текстурная «плата». Это осознанный выбор (без него не было бы 3D-деталей без
модов), и он меняется конфигом: `blocks.base`. Вот тут как раз и есть способ
сломать то, о чём спрашиваешь, — **вручную**: поставь `blocks.base: JUKEBOX`, и
проигрыватели начнут выглядеть как платы, а вставленная пластинка перестанет быть
видна (её модель — часть модели блока). Дефолт `SMOOTH_QUARTZ_SLAB` выбран именно
потому, что это «строительный» блок, а не игровой механизм.

## 4b. Руды: геология, зачистка и плавка

Элементы нельзя просто «найти в земле»: ванильная руда — это ванильный лут, а
свою текстуру на чужой блок мы не вешаем (клиентских модов не делаем). Поэтому
жила живёт у плагина и описывается **функцией**, а не блоками: из координат
чанка и сида мира детерминированно следует, есть ли здесь жила, какая, какого
размера и на какой глубине. Отсюда полезные свойства: жилу нельзя «вычерпать»
половиной мира и затем потерять, она на месте после перезагрузки, и её не нужно
генерировать при создании мира.

* **Жила** — это руда (медь / олово / цинк), размер 14…40 блоков и пояс по Y из
  `config.yml`. Пока жила **не вскрыта**, копка породы даёт обычную породу.
* **Геозонд** (`geoprobe`, инструмент): ПКМ по породе — либо «здесь пусто»,
  либо направление, дистанция, глубина и сколько блоков осталось. ПКМ внутри
  жилы её вскрывает (после этого копать можно), и тратит 1 прочность.
* **Кусок руды** (`raw_copper_chunk` и др.) падает с блоков внутри вскрытой
  жилы вместо булыжника. Два куска → один **слиток** в обычной печи: это
  настоящий `FurnaceRecipe` с `ExactChoice`, потому что наш предмет — тот же
  ванильный полублок, и в JSON-рецепте его не описать.
* **Зачистка/лужение**: `wire_stripper` (ПКМ в воздухе с шифтом) превращает
  изолированный провод в голый монтажный; лудят его на столе — голый провод +
  припой + абразив → `wire_tinned`.
* Дальше цепочка идёт через паяльный стол (`Soldering`), и её часть — **наши**
  предметы, поэтому она не в `Recipes.DEFS`, а в таблице `OUR_INGREDIENTS`:
  2 слитка меди + 2 нитки → голый провод; голый провод + припой → лужёный;
  2 слитка цинка + уголь + нитка → воздушно-цинковый элемент; лужёный провод +
  кварц 16 МГц + припой + флюс → микроконтроллер.

Всё это считается в `deposit/Deposits.java` — классе, который не знает про
Bukkit, поэтому проверен офлайн (`tools/TestDeposits.java`, 16 проверок:
детерминированность поля при одном сиде, частота жил против конфига, пояс Y,
«пока не вскрыта — не копается», выработка до нуля, формат файла).

## 4c. Микроконтроллер: аналог Ардуино на C-подобном языке

`mcu_atmega328` — 6 ног: **0 = VCC, 1 = GND, 2…5 = программируемые порты**
(`up`/`down` — запасные). Деталь работает по-настоящему: её ноги — узлы вашей
цепи, а не красные лампочки.

* Выход — **источник Тевенина**: ЭДС = `VCC × уровень`, сопротивление порта
  25 Ом, предел 40 мА/нога. Просадка и коротыш видны решателю: в коротыше порт
  отдаёт 40 мА, а не 120 (мягкий лимит — сопротивление ключа растёт, как у
  настоящего транзистора; «идеальный генератор тока» на оборванном узле
  поднимал 40 кВ, и решатель это честно показывал).
* Вход — hi-Z: напряжение узла читается как цифра (порог VCC/2) и как АЦП
  (0…1023). Питание обязательное: при VCC < 2.6 В чип останавливается и
  отпускает ноги (brown-out), потребление самой микросхемы — 470 кОм.
* Прошивка пишется в книге для записи (в GUI поля ввода нет — это единственный
  способ набрать многострочный текст без клиентского мода), открывается с
  `programmer_usb` в 4 блоках от чипа: там же live-показатели ног — направление,
  уровень, вольты, АЦП, миллиамперы и текст ошибки компиляции со строкой.
* Язык — подмножество Arduino: `pin N input|output|pwm;`, `digitalWrite(N, HIGH)`,
  `analogWrite(N, 0..255)`, `delay(мс)`, `if (...) { } else { }`,
  `while (...) { }`, сравнения `== != > < >= <=`, `digitalRead`/`analogRead`,
  `//` комментарии. Переменных, функций и арифметики нет сознательно: состояние
  системы — это уровни на ногах, и их видно в GUI.
* Исполнение — cooperative, внутри шага симуляции (20 Гц): за тик не больше 64
  операторов, `while` ограничен 64 повторами, `delay(50)` = один тик. Бесконечный
  цикл не подвешивает сервер — он просто жжёт квоту.
* Текст прошивки хранится на диске (`"p"` в `registry.json`), а вот ноги и
  счётчик команд — нет: после перезагрузки сервера чип стартует сначала, как
  настоящая Arduino после сброса питания.

Интерпретатор — `fw/Firmware.java`, тоже без Bukkit: `tools/TestFirmware.java`
проверяет компиляцию, номера строк ошибок, переходы `if/else` (главная ловушка —
else), квоту `while`, `delay` в тиках и АЦП (21 проверка).


## 4d. Привод: девять деталей механики (v1.4.0)

Механика живёт поверх электрики, а не рядом с ней. Три новые id — обычная цепь
(`supply_220v` 220 В с внутренним сопротивлением 6 Ом, `motor_220v`,
`fuse_slow_10a`), а шесть — `kind: KINETIC` с **нулём выводов** (ветка
`MAGNET, STATION, TOOL, SUPPLY, KINETIC -> 0` в `Components.defaultPins`):
вал, редуктор, маховик, колесо, пила, бур. Роль деталь берёт из `shape`
(`shaft|gear|flywheel|wheel|saw|drill`), цепь они не замыкают — у вала выводов
ноль, и решатель его просто не видит.

Связь одна, но настоящая: **момент мотора — это ток обмотки, а ток — это
ЭДС вращения**, то есть обороты.

```
I = (Uклемм − Φ·ω) / Rобм.        M = Φ·I         ω̇ = (M·i·η − Mнагр.) / J
```

Поэтому пила, упершаяся в бревно, реально садит вал: нагрузка есть — обороты
падают — ЭДС падает — ток и момент растут. Пустой вал крутится «по напряжению»
и момента почти не просит. Всё это считается в `Kinetics.step()` (без Bukkit,
38 офлайн-проверок в `tools/TestKinetics.java`), а `KineticEngine` раз в такт
берёт жёсткий кластер соседних деталей (`/elec rig`) и отдаёт решателю долю
паспортных оборотов — той долей он поднимает ЭДС.

Что игрок видит руками (числа — из самотеста, `selftest: true`):

* **Пуск — это событие.** Мотор 220 В на обмотке 22 Ом в стоке даёт
  7.86 А и 5.90 Н·м. Бревну нужно немного — а вот трение опор съедает всё:
  та же сборка на камне просила 4.62 Н·м, на рельсе — 0.96 Н·м. Не хватило
  момента — вал не набирает, и на клеммах висит 1.7 кВт при норме 500 Вт;
  обмотка копит перегрузку и горит через ~26 с («перегрев: P=1.73 кВт при
  норме 500 Вт») — это таймер, а не выстрел в первом такте. С `gearbox_3x` момент на пиле
  15.9 Н·м — **×2.7, а не ×3**: у пары КПД 0.9, и это ровно то, почему
  редуктор греется. Дальше 6 брёвен за 30 с при 1269 об/мин и 425 Вт на валу.
* **Маховик копит, а не создаёт.** 0.4 кг·м² на 1757 об/мин — 6.7 кДж, и
  каждый удар стоит четверти запаса: одно бревно (1500 Дж) снимает 1200 Дж и
  роняет колесо до 1593 об/мин. Дальше крутит только мотор. Разгон
  привода с нуля — 14.7 с: это инерция, а не лаг решателя.
* **Трение опор — это μ под колесом.** 0.005 (рельс) против 0.35 (камень):
  на камне каретка стоит («тяги не хватает: нужен редуктор побольше, колесо
  помельче или опора легче»), на рельсе едет 2.75 м/с. В учебной сборке под
  колёсами лежит `RAIL` именно поэтому — иначе вся сборка стоит на трении.
* **Механика бьёт по цепи обратно.** Бур в упор о камень: 7.86 А держатся, и
  `fuse_cartridge_5a` (I²t 45) по накопленному «перегреву» говорит
  «держишь ещё 1.23 с» — ровно столько, чтобы игрок успел убрать упор.
  Накопленный I²t считается только от превышения (голый I²t сжигал вставку
  и на паспортном токе), поэтому 800 мА через вставку на 1 А живы 30 с.
* **Нормы на отлуп.** `kinetics.break-blocks` (да) и
  `kinetics.blocks-per-minute` (40) — без них механизм превращает склон в
  щебень за минуту. Лимит — скользящее окно в минуту **на каждый механизм**, а
  не глобальное: перепилил — и в подсказке `лимит 40 блоков/мин на механизм`,
  а не молчание. Тот, что упал без инструмента (отрезали опору), подписан
  отдельно: `срублено блоков: N — дальше работала гравитация`.

`/elec rig` — что берёт ближайший механизм (обороты вала и мотора, момент,
тяга каретки, последний комментарий); `/elec rig place` собирает учебную
лесопилку у спавна (консоль — `rig place <мир> <x> <y> <z>`), `/elec rig undo`
её разбирает и возвращает блоки как было. Живая проверка в самотесте крутит
движок вручную 600 шагов и требует `блоков срублено > 0` плюс чистого отката.

## 4e. Свинцовый аккумулятор: банка, которая помнит (v1.6.0)

Крона 9 В отдаёт 9 В вечно — она `SOURCE`. Настоящая банка так не умеет: у неё
есть запас, и он кончается. Добавлен вид `battery_lead_12v` («Свинцовый
аккумулятор 12 В / 7 А·ч», `kind: BATTERY`, паяется) — первый компонент, который
**помнит, что с ним делали**, и помнит это после рестарта сервера.

| Что считает | Как | Числа из теста (`tools/TestBattery.java`, 39 проверок) |
| --- | --- | --- |
| ЭДС от заряда | `E = 12.65 − 0.80·(1 − soc)` В | 20 % → 12.01 В, 80 % → 12.49 В: 0.48 В на 60 % заряда, вольтметром SOC не измерить |
| Ампер-часы | `Δsoc = I·Δt / (3600·C)` | 3000 шагов схемы через 10 Ом (живой прогон): 1.26 А, +0.0263 А·ч отдано, остаток 99 % |
| Эффект Пейкерта | `C(I) = C_p / I^(n−1)`, n = 1.25 | 0.35 А (C20) → все 7.00 А·ч, 0.7 А (0.1C) → 5.89 А·ч (84 %), 35 А (5C) → 2.21 А·ч: большой ток съедает ёмкость |
| КПД заряда | `charge-efficiency` = 0.95 | час заряда 1 А возвращает 13.4 % вместо 14.3 %; а чтобы *отдать* 1 А·ч при 1 А, банка теряет 18.8 % заряда вместо «чистых» 14.3 % — это Пейкерт на разряде |
| Севшая банка | `r_int ×40` при soc < 5 % | `r_int` полной банки 0.020 Ом, севшей (soc < 5 %) — 0.800 Ом: при 1.26 А внутреннее падение 0.03 В против 1.01 В у пустой, и вместо 12.62 В на клеммах остаётся ≈10.8 В — лампа тускнеет задолго до «нуля на вольтметре» |
| Сульфатация | 2 % ёмкости в час простоя ниже 20 % | сутки в нуле — минус 48 % ёмкости; при потере ≥ 50 % деталь становится `burnt` |
| Кипение | \|U\| > 14.4 В **или** ток > 1C | 15 В / 20 А — потеря 3.9 % ёмкости за час; штатные 13 В / 6 А — ёмкость цела и отказа нет; 12 А при 13 В — отказ по току, хотя по напряжению всё в норме |
| Нагрев | `I²r + I·Uпад`, остывание `k·ΔT` | коротыш на 35 А: +28.8 °C за минуту (36 Вт); нагрев ползёт к равновесию `P/k`, а не в бесконечность (+38.9 °C через 31 мин при потолке 40.7), в покое остывает до +0.00 °C |
| Саморазряд | 4.8 % в сутки | полный банк за сутки теряет 4.8 % заряда; «идеальный» режим — 0 в конфиге |
| Полная банка | `soc = 1` и тока нет | состояние `closed`: «полоска замкнута», отказа нет |

Состояния задействованы все шесть, и каждая подпись говорит то, что видно по
числам: `off` — покой, `closed` — полна в покое, `dim` — разряжает, `rev` — ток
идёт обратно в банк (его заряжают), `on` — заряд выше предела, «кипит»,
`burnt` — деградация или перегрев. Подпись на грани — `12.42 В · 40 % ·
разряд 2.1 А` (эту строку сверяет и офлайн-тест), а `/elec dump` у банки
dопиcывает формат `N %, через клеммы ±X.XXX А·ч, потеря ёмкости D %`, и ещё
`+T °C`, если банк нагрет больше чем на полградуса.

**Чего модель честно не делает.** Она не различает «банка стоит навыворот» и
«как надо»: знак напряжения на выводах зависит от того, к каким узлам попали её
контакты, а не от полярности детали (проверено: та же банка при ориентации 3 в
одиночной цепи отдаёт, при ориентации 1 принимает). Различить это можно только по
соседю — две банки в параллель, одна reversed, — а решатель работает с модулями.
Значит, «детектор переплюсовки» был бы обманом ученика, и его в модели нет.
Достоверно модель знает ровно то, что знает настоящая банка по своим клеммам:
сколько энергии приняли и отдали, каким током и как нагрелись.

**Где живёт состояние.** `CompInstance.aux`: разряженность (`1 − soc`), потеря
ёмкости, ампер-часы через клеммы, нагрев. Хранится именно `1 − soc`, поэтому у
свежей детали aux нулевой — банк полон, никакой инициализации не нужно.
`Persistence` пишет ненулевой `aux` в `registry.json` (`"a":[…]`), так что заряд,
кипение и сульфатация переживают рестарт.

**Настройки** — `config.yml`, блок `battery:` (`charge-efficiency` 0.95,
`self-discharge-per-day` 4.8 %, `sulfation-per-hour` 2 %).

**Как получить.** 3×3: `I I / PRP / CWC` (железо — клеммы, чёрный бетон — корпус,
redstone — масса, медь — токоотводы, склянка — электролит), затем пайка
паяльником; в JEI/REI/EMI видно и то, и другое.

## 4f. Рукоять, водяное колесо и машинный генератор (v1.7.0)

До этой версии механика умела только есть электричество: `motor_220v` крутил вал,
остальное было нагрузкой. Добавлены три детали, у которых роль обратная —
**механика сама становится источником**, а четвёртая превращает вращение в ток.

| Деталь | `kind` | Паспорт | Что делает |
| --- | --- | --- | --- |
| `crank_hand` «Ручная рукоять (мускульный привод)» | `MOVER` | 90 Вт, 90 об/мин | крутит вал, пока по ней жмут ПКМ; один щелчок даёт 0,55 с запаса хода, дальше рука обязана вернуться — «крутить вечно, один раз нажав» модель не позволяет |
| `wheel_water` «Водяное колесо» | `MOVER` | 150 Вт, 26 об/мин, 55 Н·м на мокрую грань | тянет моментом от воды: считаются четыре боковые грани (потолок 220 Н·м) и напор сверху — по +25 % на каждый лишний блок воды |
| `dynamo_12v` «Машинный генератор 12 В» | `DYNAMO` | 12 В при 1500 об/мин, обмотка 0,8 Ом, 5 А долго | отдаёт ток в цепь **из оборотов вала**: не крутят — машина просто обмотка, крутят — источник; тот же ток её и тормозит |

| Что считает | Как | Числа (`tools/TestMovers.java` — 21 проверка, `tools/TestDynamo.java` — 32) |
| --- | --- | --- |
| Кривая движителя | `τ(ω) = τ₀·(1 − ω/ω₀)`, `τ₀ = 4P/ω₀` | рука: `τ₀ = 38.2 Н·м` на стопе («~95 Н на рычаг 0.4 м» — реально удержать двумя руками), максимум 90.0 Вт на 45 об/мин; быстрее холостых — момент нулевой, разогнаться «в гору» нельзя |
| Вода на лопатках | 55 Н·м × грани, ×4 грани максимум, +25 % напора на блок | 4 блока: 220 Н·м, 8 блоков: те же 220 Н·м (граней-то шесть); 1 блок воды сверху → 220 Н·м, 3 блока → 330 Н·м |
| Трение самого вала | `Spec.dragNm`: 1.0 Н·м у рукояти, 1.5 Н·м у колеса — **не** доля подводимого момента | вал под рукой держит 89 об/мин вместо «круглых» 90, а «руки убраны» → 0 об/мин за 20 с модели. Без этой строчки механизм, который больше никто не крутит, крутился бы вечно (старая модель трения = 6 % от момента: при нулевом моменте и трения ноль) |
| ЭДС машины | `E = U₀·min(ω/ω₀, 1.5)` | 750 об/мин → 6.00 В; паспортные 1500 → 12.00 В; разнос ограничен 1.5×: 3× паспортных дают 18 В, а не 36 — щётки уже летят |
| Щётки | `BRUSH_V = 0.6 В` | 60 об/мин → ЭДС 0.48 В, и наружу ничего не выходит: пока ЭДС не превысила 0.6 В, машина молчит. Отсюда и редуктор в учебной сборке: рука даёт 90 об/мин, ×9 → 810 об/мин, 6.5 В — и светодиод/лампа загораются |
| Ток и момент | `I = (E − Uщеток − Uклемм)/r`, `τ = k·I`, `k = U₀/ω₀` | короткое замыкание: 14.25 А — «вот почему без предохранителя нельзя»; k = 0.0764 В·с/рад → 2 А дают 0.15 Н·м тормоза; момент не зависит от знака тока — тормозит в обе стороны |
| Энергобаланс | `τ·ω = U·I + I²r + I·Uщеток` | 21.000 Вт на валу = 17.500 Вт в цепь + 3.500 Вт в тепло (сходится до 1e-9); момент тормоза пересчитывается на сторону привода ×редуктор, иначе генератор за тремя редукторами отдавал бы 273 Вт при руке на 90 Вт — «вечный двигатель» самотест ловит прямо в мире |
| Нагрев и смерть | 260 Дж/°C, остывание 0.8 Вт/°C (τ ≈ 325 с, аналитический шаг, не Эйлера) | +4.4 °C при 3.5 Вт потерь, в покое остывает до +0.000 °C; коротыш на полчаса → +214 °C и повреждение 100 %, и остыв, машина уже не восстанавливается |
| Счётчики | `aux[0..3]` = °C, А·ч, Вт·ч, повреждение | час током 2 А = 2.00 А·ч и 22.34 Вт·ч (не 24: полватта ушло на щётки); принятый ток пишется минусом — машину крутят как мотор |
| Состояния | `off` / `dim` / `on` / `rev` / `burnt` | «горит» = отдаёт, «тускло» = крутится без тока (клеммы висят), «обратно» = электротормоз, `burnt` = сгоревшая обмотка; подписи: «мало оборотов: 100 из 1500 — ЭДС 0.80 В, на щётках гаснет 0.6 В», «перегруз: 6.0 А при долгом допустимом 5.0 А» |

**Как выглядит в игре.** Учебная сборка `/elec rig place` теперь строит вторую
установку — «свет от собственных рук»: рукоять → маховик → два редуктора ×3 →
генератор → провод → лампа → земля, и рядом водяное колесо в воде. Прогон на
живом сервере (Paper 1.21.11 b132, `mc68.log`; там же — строки про датапак и про
крафты из реестра, §4g и §4h):

```
PASS рукоять крутит генератор: рукоять и колесо собраны у 60,-59,60 | вал под рукой 89 об/мин
(пик разгона 292), после «руки убраны» 0, колесо в воде 25, без воды 0; генератор: 367 мА,
6.20 В, +0.0020 А·ч / 0.02 Вт·ч, нагрев +0.0 °C; снято с вала 2.39 Вт; лампа: горит 0.76,
ток в цепи 367 мА
PASS водяное колесо: крутится, стоя в воде, и встаёт без неё (порог: более 5 об/мин в воде
и менее 30 % от пика на воздухе)
```

Там же видно «2.39 Вт с вала» против `6.20 В × 367 мА = 2.28 Вт` в цепи —
остальное съели щётки и обмотка, и это ровно то, что показывает офлайн-тест.

**Что модель честно не знает.** Вода не течёт: считается только число мокрых
граней и высота столба, «река с быстрым течением» и «лужа под колесом» для неё
одинаковы. Знак тока машина берёт из узлов, а не из «направления намотки», —
поэтому переплюсовать генератор так, чтобы он стал мотором, можно любой деталью
с питанием: за этим надо следить, как за настоящей банкой. И самое главное:
как выглядят три новые текстуры в глазах игрока, из песочницы проверить
нельзя — видно только то, что нарисовал генератор, 1695 разрешённых ссылок
и 0 битых в `tools/check_pack_refs.py`.

**Настроек нет ни одной новой.** 90 Вт человека, 55 Н·м воды, 0.6 В щёток и
325 с остывания — это константы физики в `Movers.java` и `Dynamo.java`, а не
рычаги под капотом: их сверяют офлайн-тесты, и «подкрутить конфиг, чтобы рука
выдавала киловатты», игрок не сможет.

**Как получить.** Рукоять: 2 железных слитка + палка (`II / ·I· / ·S·`), колесо:
доски и железные решётки (`P P / PWP / P P`) — их не паяют, как вал и шестерни.
Генератор спаивается на столе: `ICI / CWC / ·R·` (железо — корпус, медь —
обмотка, золотой блок — коллектор, redstone — токоподвод); в сетке намеренно
оставлена пустая клетка: паяльный стол обязан влезть в тот же рецепт, иначе
витрина JEI показывает деталь без станка (самотест это и проверяет:
`стол в сетке рецептов: 69/69`).

## 6. Ресурспак: что генерируется

`python3 tools/gen_pack.py` кладёт в `build/resourcepack/`:

* `assets/electronics/textures/item/<id>_<state>_{top,side,bottom}.png` —
  процедурные текстуры 32×32, доведённые до вида ванильного ресурса (у LED и
  ламп виден «глазок», у резисторов — цветовые кольца номинала, у БП —
  дисплей, у «сгоревшего» — трещины, у «обратного» — красный крест, у
  «замкнутого» — зелёная скоба). Все три вида проходят финальный проход
  `mc_texture()`: сетка 16 px (клетки 2×2, назад только NEAREST), палитра в 20
  цветов median-cut — и только там, где оттенков больше 26 (иначе 1-px цифры
  семисегментника сливались с панелью), дизер Bayer 4×4 вместо мягкого края
  там, где прозрачность, зерно ±9/255 на трети пикселей и три тона граней
  (верх ×1.16, середина ×0.91, низ ×0.80) — объём у блока без света берётся
  ровно оттуда. Без прохода деталь выглядела иконкой из модификации: канва
  рисовалась сглаженными градиентами, а `side_from_top` тянул crop BICUBIC.
  Последнее важно вдвойне: модели рендерятся с `minecraft:cutout`, который
  отбрасывает каждый пиксель с α < 128, — из-за размытия по силуэту в гранях
  были дыры, а подсветка `on` (прямоугольник с α=60) и нагар `burnt` (α=70) на
  боковинах не рисовались в игре вовсе; теперь они смешиваются с самим
  изображением и остаются сплошными. Замерено на паке: пикселей, которые
  cutout вырезает, 473 722 → 314 568, средняя светлота та же (94.8 → 95.0),
  ни одна текстура не потеряла покрытие (максимальная дельта по файлу — 0);
* `assets/electronics/models/item/<id>_<state>.json` — модель блока 16×16×16
  c нужными `display`-трансформами (`fixed` — для ItemDisplay, `gui` — для
  инвентаря);
* `assets/electronics/items/<id>.json` — **состояние модели**: `select`/
  `range_dispatch` по `custom_model_data[0]` для «лампочных» типов, иначе
  базовая модель (состояние всё равно задаёт `item_model`);
* `assets/minecraft/atlases/blocks.json` — без этого в 1.21.9+ свои текстуры
  не сшейвятся в атлас;
* перекраска `minecraft:smooth_quartz_slab` → зелёная «плата» (это блок-основа
  из `config.yml: blocks.base`);
* `lang/ru_ru.json`, `lang/en_us.json`, `pack.mcmeta` (64..75: `pack_format` +
  `supported_formats` + `min_format`/`max_format`), `pack.png`.

**Свои текстуры: `users_textures/`.** Всё, что перечислено выше, — процедура, и
её можно перебить своими рисунками: кладёте PNG в `users_textures/` с именем-
**тегом**, и `bash tools/user_pack.sh` пересобирает пак и `build/preview.png`.
Порядок поиска (первое найденное выигрывает): `<id>_<состояние>_<грань>.png` →
`<id>_<состояние>.png` (это только про `top`) → `<id>_<грань>.png` → `<id>.png`.
Последний вариант и есть самый полезный: **одна** текстура становится канвой, из
которой генератор сам выводит `dim`/`on`/`burnt`/`rev`/`closed`, боковину и низ,
— дорисовывать шесть состояний вручную не нужно. Свои файлы не проходят через
`mc_texture()` (иначе человек получил бы не то, что нарисовал): к ним применяются
только пиксельные операции состояний. Отдельные теги `host_top|side|bottom.png`
перекрашивают саму «плату» (`minecraft:smooth_quartz_slab`).
Полный список тегов — **1695** штук, по числу текстурных слотов, — с названиями
блоков по-русски и по-английски, палитрами и ванильными привязками лежит в
`users_textures/README.md`; он генерируется (`python3 tools/user_tags.py doc`) из
кода генератора, поэтому не может устареть. `python3 tools/user_tags.py check`
скажет, что из положенного реально будет взято (и подскажет ближайший тег, если
вы опечатались), `--example` положит заготовку. Пока в `users_textures/` пусто,
пак байт-в-байт равен выпущенному: `1726a3acfa1a3ba80c77610f277f8826ec238e55`.

### 4h. Крафт в верстаке описан один раз (v1.7.2)

Рецепт детали живёт в реестре — `components[].craft` в `shared/components.json`:

```json
"craft": {"shapeless": {"copper_ingot": 1, "honeycomb": 1}, "count": 1}
"craft": {"pattern": ["GGG", "CRC", "GGG"],
          "key": {"G": "gold_nugget", "C": "copper_ingot", "R": "redstone"},
          "count": 1}
```

Из него растут обе стороны: `Recipes.loadFromRegistry()` регистрирует крафт на
сервере (имена ингредиентов разрешаются через `Registry.ITEM`), а
`tools/gen_pack.py::load_recipes()` пишет файл датапака. До этого таблицы было
две — `Recipes.DEFS` (18.7 КБ literal-ов) и `RECIPES` в генераторе (16 КБ), —
и они успели разъехаться: `bench` в датапаке собирался из **бумаги** и отдавал
**×2**, в плагине — из **плиты-основы** и **×1**; провода `wire_red|black|yellow|blue`
датапак выдавал по 4 штуки, плагин — по 1; `solder`/`flux`/`desolder_braid` — ×2
против ×1. Теперь `count` читает и плагин, так что сборка с датапаком и без него
даёт одинаковый результат.

Что это стоило: из репозитория убрано ~35 КБ дублирующихся таблиц, `craft`
попал в `tools/check_pack_refs.py` (pattern ≤ 3×3, каждый символ паттерна описан
в `key`, `count` 1..64, имена — ванильные item id), так что кривой крафт виден
офлайн, а не в логе ядра. Миграция проверена сравнением архивов: из 38 файлов
датапака семантически изменился **ровно один** (`bench.json`), остальные
отличались только порядком ключей в JSON, а ресурспак после рефактора
байт-в-байт прежний. Живое подтверждение — новая строка `selftest`:
`PASS крафты собраны из реестра: неразобранных ингредиентов 0,
верстачных 38/(нужно 38, плавка 3)`, счётчики в логе не сдвинулись
(`зарегистрировано рецептов: 41 (пайка: 69 витрин для JEI, пропущено 7, плавка 3)`),
всего `32 PASS / 0 FAIL / 0 [ERROR]` (`srv/mc68.log`).

### 4g. Почему паки v1.7.0 не работали (и что изменилось в v1.7.1)

Три независимых бага, каждый со своим следом в логе сервера:

1. **Заголовок пака.** `pack.mcmeta` объявлял только `pack_format`. С 1.21.9
   пара `min_format`/`max_format` обязательна, иначе сервер пишет
   `Pack declares support for version newer than 81, but is missing mandatory
   fields min_format and max_format` — и пакета нет вовсе. Теперь генератор
   (`tools/gen_pack.py` → `mcmeta()`) пишет обе схемы: `pack_format` +
   `supported_formats` (читают 1.21.7–1.21.8) и `min_format`/`max_format`
   (читают 1.21.9+): ресурспак 64..75, датапак 80..94 — у датапака своя линия
   форматов, 94 в нём это 1.21.11, а не «75 плюс что-то».
2. **Форма рецептов.** Ингредиенты были записаны объектами
   `{"item": "minecraft:stick"}`, а ванильный разбор ждёт **строку** (или
   `{"tag": ...}`) → `Not a string`, а для shapeless ещё и обманчивое
   `List is too short: 0`. Результат ссылался на `electronics:<id>` — такого
   ключа в реестре `minecraft:item` нет ни у кого (наша деталь = ванильный
   предмет-основа + компонент `item_model`) → `Unknown registry key` на каждом
   файле. Итого 38 «Couldn't parse data file», из них 36 — ещё до v1.7.0: баг ехал
   с v1.4.0, когда датапак появился.
3. **Распознавание собранного предмета.** Результат — `minecraft:smooth_quartz_slab`
   (для инструмента `minecraft:brush`) с `item_model` (модель), `item_name`
   (подпись из lang пака) и `custom_data → electronics:def` (метка, которую
   читает `Items.defOf`). `Items.defOf` с v1.7.1 узнаёт деталь и по `item_model`,
   если ядро не переложило `custom_data` в PDC-представление.

Проверено не скриптами, а живым сервером: Paper 1.21.11 build 132, датапак в
`world/datapacks/electronics-recipes-datapack.zip`. Лог:
`Found new data pack file/electronics-recipes-datapack.zip, loading it
automatically`, ноль строк `Couldn't parse data file` (было 38), и новая строка
самопроверки `PASS датапак: рецептов 38/38 приняты ядром под ключом
electronics:<id>, модель результата — у 38, деталь опознаётся в 38/38`.
Офлайн-страховка: `tools/check_pack_refs.py` валидирует и поля `pack.mcmeta`, и
форму всех рецептов (`рецептов 38, ошибок формата 0`). Полный лог прогона —
`srv/mc66.log` (31 PASS) и `srv/mc68.log` (32 PASS), 0 FAIL, 0 ERROR,
0 строк `Couldn't parse data file` в обоих.

Всего 3071 файл: 1695 текстур предметов (32×32), 684 модели состояний
(по 6 на каждый из 114 видов), **684** `items/*.json` — 114 базовых с
`range_dispatch` по `custom_model_data` и по одному на каждый адрес состояния
(`_dim`/`_on`/`_burnt`/`_rev`/`_closed`), 3 текстуры перекрашиваемого слаба,
атлас, 2 lang-файла, `pack.png`, `pack.mcmeta`. Плагин может запросить 3390 индексов состояния
модели (`Σ states × 6` — шесть ориентаций выбираются свойством `orientation`
в той же модели) — все они покрываются этими 684 моделями.

Архивы собираются детерминированно: записи в `zip` отсортированы, дата в
заголовке зафиксирована (1980-01-01), права постоянные — иначе `zipfile` пишет
туда mtime файла, и два прогона генератора дают разные байты при идентичном
содержимом, то есть сборку нельзя ни закэшировать, ни сверить по sha1.
Проверено на v1.7.1 (замеры этого прогона, оба пака пересобраны вместе с
исправлением формата): два последовательных `python3 tools/gen_pack.py` дают
`1726a3acfa1a3ba80c77610f277f8826ec238e55` (ресурспак, 2 873 794 Б) и
`30867db59677cee56c696ef6dcf9357254402b91` (датапак) в обоих прогонах. На v1.7.2
датапак пересобран из единого поля `craft`: 15 135 Б, `fa20b9f3e8308f16275e5d7f56e73e4fc381f10b`
(ресурспак от рефактора не изменился вовсе — снова `1726a3ac…`).

**Почему у всех деталей ровно 6 состояний.** Раньше у 17 деталей `states`
был 1 или 2 («им нечего показывать»), но `Def.clampState()` обрезает запрос до
`states-1` — то есть `state=ON` у вентиля/прибора превращался в `dim`, а
`BURNT` у резистора вообще не мог отрисоваться. Теперь `states: 6` у всех
электрических позиций (кроме инертных `BOARD`/`CUTTER`/`EMPTY`/`SCHEMATIC`),
и у шести деталей привода (§4d: им нужны `off`/`on` плюс `dim` на просадке
вала), а `tools/check_pack_refs.py` следит и за этим, и за тем, чтобы
`meta.state_model_count` совпадало с Σ(`states`×6) (проверено: при
`states: 2` или левом `meta` — `ПОЗОР…` и код возврата 1). У резисторов и
подстроечника появился `glow_color: [255,110,30]`, так что `on` — это рыжее
«раскалённое» тело, а не молочно-белое: средний цвет текстуры
`resistor_330r_top` сместился с `#aa9e8a` (покой) на `#ca9773` (перегруз),
`burnt` — `#4d3f37` (все три числа посчитаны по PNG текущего пака, α ≥ 128).

Полный каталог всех 114 деталей с номиналами, флагами и диапазонами индексов —
`docs/blocks.md` (генерирует `python3 tools/catalog.py`). Листы текстур для
быстрого просмотра: `release/textures/sheet-01..09.png`
(`python3 tools/sheets.py`).

`release/electronics-recipes-datapack.zip` — 38 рецептов
(`data/electronics/recipe/*.json`): то, что паяется, в датапак не попадает (69
спаиваемых id — см. «Пайка»), а совпадают они с серверными или нет, следит
`Recipes.register()`: на живом сервере лог говорит `зарегистрировано рецептов:
41 (пайка: 69 витрин для JEI, пропущено 7, плавка 3)`, то есть 110 рецептов
видят игроки, и все 114 id есть в `Material` (раньше одного не хватало).

`python3 tools/check_pack_refs.py` сверяет, что все 114×6 ключей моделей,
которые может запросить плагин, существуют в паке и что все ссылки на
текстуры разрешаются (сейчас: 1695 ссылок, 0 битых).

Совместимость пака по версиям — в `docs/pack-compatibility.md`.
Как добавить свою деталь (полный путь: реестр → пак → решатель → крафт →
тесты → релиз) — в [`docs/adding-parts.md`](docs/adding-parts.md).


## Где это лежит

Репозиторий: **https://github.com/amir2013shai-byte/electronics-mc** (ветка `main`).
Сборка на каждый push — GitHub Actions (`.github/workflows/build.yml`): `mvn package`,
`tools/publish.sh`, `tools/run_tests.sh`, `check_pack_refs.py`, проверка
`pack_format == 75`; артефакты уходят и в artifacts раннера, и (на теге `v*`)
в GitHub Release. Сборка воспроизводима: в `pom.xml` задан
`project.build.outputTimestamp`, поэтому два подряд `clean package` дают
**одинаковый** `Electronics-1.7.1.jar` (на v1.6.0 проверено заново:
`5651448dd85b90af51e20a2fcab84447f0f9528e` в обоих прогонах, 372 393 байта;
историческая проверка v1.4.0 — `ca9047ad5e86ce6554785047cc770b98fb9c84db`, 348091); ресурспак и датапак теперь тоже воспроизводимы по байтам — см. §6 — sha1 из `release/sha1sums.txt` имеет смысл.

**Как называется jar.** С v1.6.0 — `Electronics-<версия>.jar`, номер в имени
несёт настоящую версию плагина, а берётся она из одного места, `plugin.yml`:
`tools/publish.sh` копирует сборку в `release/Electronics-$VER.jar` и выбрасывает
старые имена, CI и `tools/release.sh` путь не хардкодят (маска
`release/Electronics-*.jar`), а `tools/run_tests.sh` следит, чтобы `plugin.yml` и
`<version>` в `pom.xml` не разошлись — иначе в `plugins/` лёг бы файл с номером,
который никто не проверял. Ту же версию сервер печатает при включении и её же
показывает `/version Electronics`.

**Готовые файлы:** Releases → последний релиз → Assets: `Electronics-<версия>.jar`,
`electronics-resourcepack.zip` (ставить в `resource-pack.url` на сервере или в
`.minecraft/resourcepacks`), `electronics-recipes-datapack.zip`, `preview.png`
(все 114 предметов на листах `sheet-01…09`), `scope-screen.png` (кадр экрана
осциллографа — собран тем же кодом, что рисует его в мире) и `sha1sums.txt`. Тот же набор лежит в
артефактах любого рана Actions (`electronics-1.21.11`).
