# Как в проект добавляется деталь (полный путь)

Документ описывает, что именно нужно сделать, чтобы в `electronics-mc` появилась
ещё одна электрическая деталь — не картинка, а предмет, который считают решатель,
добывают, паяют, видят в JEI и проверяет `selftest`. Всё по фактическому коду
(`v1.3.1`), с названиями методов и файлов.

---

## 0. Правило приёмки

Деталь считается добавленной, когда выполнены **девять** пунктов. Половинки в
проекте не приживаются: каждая строка ниже уже ловила баг.

1. **Трёхмерность — только ресурспаком.** Никаких клиентских модов, никаких
   своих блоков: предмет носит ванильный «носитель», а модель ему даёт пак
   (`items/*.json`). Это и есть та самая идея «800+ состояний игрока».
2. **Запись в реестре** `shared/components.json` (+ зеркало в ресурсах плагина).
3. **Деталь электрически настоящая**: у неё есть вывод(ы), она попадает в MNA и
   меняет токи/напряжения так, как это делает живой компонент.
4. **Крафт реальный и трудный**: паяется на столе (`meta.soldered`) или делается на
   станке (`Metallurgy`), ванильный рецепт — только из ванильных материалов.
5. **JEI**: для спаечных деталей — «витрина», для ванильных крафтов — обычный
   рецепт; обе таблицы обязаны совпадать с `Recipes.DEFS`.
6. **Каталог**: `/elec show` умеет объяснить, что это и зачем; у `kind` или у id
   есть текст, иначе `selftest` ругнётся.
7. **`selftest`**: строка PASS с настоящими числами (амперы, вольты, градусы),
   а не «код вернул true».
8. **Живой прогон на Paper 1.21.11**: jar закинут на сервер, `elec selftest`
   напечатал N PASS / 0 FAIL / 0 ERROR, в логе нет `[ERROR]`.
9. **Доки + релиз**: README (RU и EN), `docs/blocks.md` перегенерирован, числа в
   доках совпадают с логом, `tools/publish.sh` пересобрал `release/`, коммит,
   тег, ассеты, CI зелёный, jar из релиза побайтово равен локальному.

## 1. Где лежит истина

```
shared/components.json                      ← единственный источник
plugin/src/main/resources/components.json   ← копия один-в-один (её читает плагин)
tools/gen_pack.py                           ← читает shared/, генерит пак и датапак
```

`Components.load()` читает JSON из jar-ресурса, а **сверху** догружает любые
`.json` из `plugins/Electronics/components/` — то есть серверный админ может
добавить деталь без пересборки (правда без текстур она будет «невидимкой»:
модели-то в паке). Порядок в `components` важен: индексы состояний считаются
префиксной суммой (см. §3), поэтому **новые id дописывают в конец**, а не
вставляют в середину.

`tools/gen_pack.py` в конце сверяет: «рецепт не задан для …» — если id есть в
`meta.soldered`, он обязан быть и в таблице `RECIPES` (зеркало `Recipes.DEFS`),
иначе генератор предупреждает. Исключения перечислены в `BY_DESIGN`.

## 2. Запись в реестре: поля, которые реально читаются

Разбирает `Components.parse`. Значимые ключи:

| Ключ | Что делает | Кто читает |
|---|---|---|
| `id` | имя everywhere; `electronics:<id>` — ещё и имя модели | всё |
| `ru`, `en` | отображаемые имена + `lang`-файлы пака | `Items`, пак |
| `kind` | одна из 43 строк `Kind` | поведение по умолчанию, каталог, генератор |
| `shape` | `box/resistor/cap/wire/chip/battery/station/tool/supply/…` — как рисовать | `gen_pack` |
| `size` | [x,y,z] в пикселях канвы 16×16×16 | `gen_pack` |
| `palette` | цвета рисования; `shade()/mix()` дают полутона | `gen_pack` |
| `states` | сколько визуальных состояний (1..6) | `gen_pack`, индексы |
| `orientable` | рисуются ли 6 ориентаций | `gen_pack` |
| `pins` | сколько выводов; по умолчанию берётся из `kind` (`defaultPins`) | `Topology`, `Simulation` |
| `resistance`, `capacitance`, `inductance`, `voltage`, `r_int`, `v_forward`, `v_drop`, `rated_power`, `rated_voltage`, `max_current` | электрика | `Simulation.stampAll` |
| `heat_j`, `thermal_k`, `trip_temp`, `v_clamp`, `dropout`, `i_limit`, `i_quiescent`, `ac_hz`, `ratio`, `coupling`, `beta`, `resistance_hot`, `cold_factor` | тепловые и нелинейные модели | `Simulation` (PTC, стабы, варистор, МК, лампы…) |
| `hub` | «провод-концентратор»: все соседи объединяются в один узел | `Topology` |
| `polar`, `tunable`, `spdt`, `stack`, `solid` | полярность, подстройка, перекидной, стакается, непрозрачный блок | `Items`, `Events`, `gen_pack` |
| `glow`, `glow_color` | блок-свет вокруг детали | `Renderer` |
| `logic` | строка-марка для вентилей/транзисторов (`AND`, `NPN`, …) | `Simulation` |

Ноль в числовом поле = «не задано», и у большинства полей есть **значение по
умолчанию из `kind`**: например, `pins` для `MCU` = 6, `RELAY` = 4,
`BRIDGE/TRANSFORMER` = 4, `REGULATOR` = 3, `MAGNET/STATION/TOOL/SUPPLY` = 0,
`TRANSISTOR/POT/GATE` = 3, `SWITCH` = 2 (3 если `spdt`), остальные 2.

После правки JSON обязательно: `python3 tools/gen_pack.py` (пересобрать пак) и
`cp shared/components.json plugin/src/main/resources/components.json`
(иначе плагин и пак разойдутся — selftest это ловит, но лучше не доводить).

## 3. Как выглядит деталь: индексы и `item model`

Каждому компоненту принадлежит **срез** индексов состояния:

```
modelSlice()      = states × 6               // 6 — orientations
baseModelIndex()  = Σ modelSlice() у всех предыдущих в порядке реестра
stateModel(s, o)  = base + clamp(s) × 6 + clamp(o)
```

Сумма по реестру — это и есть «2886 индексов состояния модели ресурспака»
(481 визуальное состояние × 6) при 100 видах. Цель «800+» была закрыта ещё на
79 деталях; теперь счётчик просто растёт.

Что делает генератор пака (`tools/gen_pack.py`):

1. **Текстуры 32×32** — рисует канвы по `shape`/`size`/`palette`
   (`base_canvas` → `apply_state` для состояний → `side_from_top`/`bottom_texture`
   для боковин), всего 1623 файла (110 видов + слаба, перекраска, превью). Любой из этих
   1623 слотов человек может перебить своим PNG: `users_textures/<тег>.png`
   (правила имён и полный список тегов — `users_textures/README.md`, его
   генерирует `tools/user_tags.py doc`), пересборка — `bash tools/user_pack.sh`.
2. **Модели состояний** — 6 на каждый вид (660 файлов) с `elements`,
   `display`-трансформом и `gui_light`.
3. **`assets/electronics/items/<id>.json`** — определяет `item model`. Для
   «диспетчерских» kind (в `dispatch_kinds`: все детали с выводами, плюс
   `MCU`, приборы, реле…) ставится
   `minecraft:range_dispatch` по `custom_model_data` (индекс 0) на состояния,
   с `fallback` на состояние 0; для остальных — одна модель.
4. **`lang/en_us.json`, `lang/ru_ru.json`** — имена.
5. **`atlases/blocks.json`** — обязательно с 1.21.9, иначе текстуры не соберутся.
6. **Датапак рецептов** — см. §5.
7. **ZIP-и + `preview.png`**.

Плагин в `Items.applyModel` сначала пробует **`meta.setItemModel(
electronics:<id><суффикс>)`** — это основной путь (1.21.4+), и именно он даёт
«наш предмет = ванильный носитель с нашей моделью». Суффикс состояния — из
`Components.STATE_NAMES` (`""`, `_dim`, `_on`, `_burnt`, `_rev`, `_closed`).
Если ядро не даёт `setItemModel`, включается **запасной** путь:
`meta.setCustomModelData(def.stateModel(state, 0))` — тот самый
плоский индекс 0..2885. Отсюда важное требование к проверкам:
`selftest` печатает `PASS модель задаётся компонентом item_model у 100/100
предметов` — то есть ни одна деталь не висит на «голом» CMD.

## 4. Электрика: куда вписаться в решатель

Три вещи нужно понять, прежде чем деталь что-то «умеет».

**Топология (`Topology`).** Узел — это **пара блоков**: «вывод детали A
смотрит в бок, в котором стоит вывод детали B». `pinDirs(kind)` задаёт, куда
смотрит каждый вывод (у `MCU` — `{n,s,e,w,up,down}` = пины 0..5, у
`REGULATOR` — `{along0,along1,a,up,down,b}`), `opposite(face)` — стыковка
граней. Провода с `hub: true` объединяют всех соседей в один узел, поэтому
«шина земли» работает как одна net-метка. Следствие: **соединить можно любые
два вывода любых двух соседних клеток**, хоть pin1↔pin1 — проверялось на
светодиоде с резистором.

**Штамповка (`Simulation.stampAll`).** На each pass each instance gets stamped
into the MNA matrix: `stamp(nodeA, nodeB, g, iSource)` — проводимость и
втекающий ток. Уже есть готовые модели: резистор/провод (G = 1/R),
ёмкость (компаньон по backward Euler), индуктивность (Norton
`g = dt / (L + dt·R)`), диод и LED через `diodeEdge`
(при `V(a)−V(b) > v_f` — ветвь `1/25` с `v_f/25`, иначе `gLeak`), транзисторы и
вентили — через `logic`, реле/геркон — перештамповкой по состоянию,
тепловые (`PTC`, `REGULATOR`, `MCU`) — с накоплением в `aux[]`,
свинцовый аккумулятор (`BATTERY`) — ампер-часами, деградацией и нагревом в тех же
`aux[]` (см. §4e README: `1 − soc`, потеря ёмкости, счётчик заряда, °C),
стабилизаторы — с отсечкой по току, варистор — утечкой, трансформатор —
связкой двух обмоток. Для своей нелинейности: добавь `case` в `stampAll`
(рядом с `case MCU -> stampMcu(c, …)`) и храни состояние в `CompInstance`.

Правило, добытое на живом сервере: **никаких идеальных источников тока**.
Попытка воткнуть в ногу МК «ровно 40 мА» (`g = 1/1e6` + 40 мА) подняла
оборванный узел до **39.2 кВ**. Правильно — источник Тевенина с мягким
лимитом: `rz` растёт, когда требуемый ток превышает паспортный
(`rz *= |iOut| / head`), и явный шунт на собственную землю, когда узел ноги
объединился с GND этой же детали (иначе ветви нет и ток читается нулём).

**Состояние (`CompInstance`) и сохранение (`Persistence`).** Короткие ключи в
`plugins/Electronics/registry.json`: `w,x,y,z,d,o,s,t,f,l,n,m` (+ `p` — прошивка
МК). Блок-носитель PDC не имеет, поэтому реестр — основной хранилище, а PDC
только дублирует `d/o/s` когда ядро разрешает. Поля, которые ты добавишь для
своей детали, живут в `CompInstance` (см. `mcuDir/mcuLvl/mcuPwm/mcuVolt/
mcuPinI/mcuHalt`) и **не сохраняются**, если это скоротечное состояние цепи:
после рестарта цепь сходится заново — как в жизни после снятия питания.

## 4bis. Механика: деталь без выводов, которая всё равно держит цепь (v1.4.0)

`Kind.KINETIC` — не проводник, и выводов у него ноль (`Components.defaultPins`
→ 0 для `KINETIC`; в JSON число выводов вообще не пишется, ключ `pins` оставь
пустым): узла у детали нет,
`Topology` её не видит, `stampAll` её не штамует. Нужны ровно две вещи — попасть
в `KineticEngine` и в ресурспак.

1. **Роль — из `shape`, не из отдельного поля.** `Def.kineticRole()` для
   `kind: KINETIC` = `Kinetics.Role.of(shape)`: `gear` → GEAR, `flywheel`,
   `wheel`, `saw`, `drill` — одноимённые роли, всё остальное → SHAFT. Новый
   инструмент = значение в `enum Role` (сейчас 6) + ветка в `Kinetics.apply()`
   (`PUSH|SPIN|DIG|SHEAR|GRIND`) + материал в таблице `Kinetics`; иначе деталь
   будет просто ещё одним валом, и `isTool()` её не посчитает.
2. **Что читается из реестра** (`Components.java:162-169`): `ratio` (1.0),
   `coupling` — КПД пары, у вала это потери подшипников (0.98), `rpm` (0),
   `inertia` кг·м² (0), `mass` кг (0), `radius` м (0.15 для KINETIC). Работа
   на блок (Дж), момент резания и число проходов живут в таблице **материала**
   (`Kinetics.WOOD`/`REFRACTORY`/…): материал берётся из блока перед деталью по
   `Material.name()`, поэтому «дерево / камень / обсидиан» пилятся уже, без
   строчки в JSON. В реестр добавляй только то, что игрок может прочитать.
3. **Мотор — не KINETIC.** Привод даёт `kind: MOTOR` с `rpm > 0`
   (`Def.drivesShaft()`), и он остаётся элементом цепи: `stampAll case MOTOR`
   штампует `G = 1/Rобм.` и инъекцию `−ЭДС/R`, где ЭДС =
   `rated_voltage × c.speedPrev`. **`speedPrev` — доля паспортных оборотов**
   (не об/с и не рад/с), и когда вал захвачен механизмом, её считает
   `updateState case MOTOR` из `kinOmega`. Перепутать единицы здесь — самый
   быстрый способ получить либо «мотор горит на холостом ходу», либо «ток
   9 мкА на заторможенном валу» (оба были).
4. **Что механике разрешено трогать в `CompInstance`:** `kinOmega` (рад/с,
   живёт между тактами; рестарт сервера обнуляет — механизм соберётся заново),
   `kinOwned` (вал захвачен кластером) и `kinTorque` — сглаженный момент
   (фильтр на 60 мс в `KineticEngine.tick`: постоянная тока якоря, и она же не
   даёт пиле «прыгать» по ударам). `voltage`/`current`/`power` для
   `kinOwned`-мотора пишет **только решатель**: у него теперь нет
   «правильного» смысла, если их подправить руками. При освобождении вала
   (`releaseOwned`/`releaseOwnedExcept`) `kinTorque` обнуляется, а `kinOmega`
   гасится в 0.6 раз — деталь после распада кластера продолжает вращаться, как
   маховик, а не замирает.
5. **Трение опор — это блок под колесом.** `buildSpec` у WHEEL смотрит
   `BlockFace.DOWN`: `isRailish()` (имя содержит `RAIL`, либо `IRON_BLOCK` /
   `GOLD_BLOCK`) → μ = 0.005, иначе 0.35. Разница — между «каретка едет
   2.75 м/с» и «тяга 0 Н, стоит на камне», поэтому учебная сборка стелет
   `RAIL` именно под две ячейки колёс. Полем реестра μ не сделали нарочно:
   игрок читает это как «поставь рельс», и это буквально правда.
6. **Нагрузка не бывает мгновенной.** `Simulation.protect()` у `Kind.MOTOR`
   копит «сколько секунд шла тройная перегрузка» (`aux[2] += (P/3Pном − 1)·dt`,
   −0.5 за такт, пока не перегружен) и сжигает после **4 накопленных секунд**
   тройной перегрузки; `c.power = |U·I|` — мощность на клеммах. Пусковой ток
   22-омной обмотки: 1.73 кВт против нормы 500 Вт → 229/1500 ≈ 0.15 с/с →
   ~26 с до «перегрева». Без этого решатель сжигал любой привод, который игрок
   успел прижать к бревну, за один такт; теперь ответ системы честный: «разгон
   15 с без редуктора — ставь редуктор либо запускай вхолостую». `aux[2]` у
   мотора свободен: `aux[0]/aux[1]` — температура и пик у тепловых деталей.
   У `battery_lead_12v` заняты все четыре: `aux[0]` разряженность, `aux[1]`
   потеря ёмкости, `aux[2]` ампер-часы через клеммы (знак: минус — приняли),
   `aux[3]` нагрев. Ненулевой `aux` `Persistence` пишет в `registry.json`
   (`"a":[…]`) — это единственный вид памяти, который переживает рестарт.
7. **Счётчики пака.** `states: 6` у каждой детали (6 ориентаций),
   `meta.state_model_count` += states × 6, `meta.soldered` — только тем id, у
   которых есть выводы: из девяти id привода спаиваются пять (`motor_220v`,
   `gearbox_3x`, `flywheel_kinetic`, `saw_kinetic`, `drill_kinetic`), а
   `supply_220v`, `fuse_slow_10a`, `shaft_kinetic`, `wheel_kinetic` крафтятся
   обычно. `tools/check_pack_refs.py` следит за обоими числами.
8. **Мир — через `demo()`/`undoDemo()`.** Любая разборная учебная сборка обязана
   возвращать блоки: `note(block)` перед `setType`, и `undoDemo()` кладёт
   сохранённый тип обратно. Проверка в самотесте требует именно этого:
   `откат вернул мир: true`.

## 5. Крафт: пайка, станки, JEI

### 5a. Пайка

`meta.soldered` = список id, которые **нельзя** собрать в верстаке. Правила
держит `Soldering`:

* `solderCost(def)` — припой 1 шт. на 2-выводную деталь, 2 шт. на многовыводную;
* `NEEDS_FLUX` — множество kind, которым нужен флюс (полупроводники, обмотки,
  приборы, `MCU`): без него «сухая» пайка бракуется;
* `HEAT_HOT = 60°` — жало греют ПКМ по печи/костру/лаве, оно остывает
  `COOL_DEG_PER_S` °/с; 20…60° — холодная пайка (припой сгорает),
  <20° — отказ;
* `IRON_LIVES = 64` — ресурс жала (носится как прочность `BRUSH`-носителя);
* `OUR_INGREDIENTS` — **наши** предметы в ингредиентах
  (`mcu_atmega328 ← wire_tinned + crystal_16mhz`,
  `resistor_shunt_0r01 ← ingot_brass`), потому что ванильный `ShapedRecipe`
  их описать не может.

`Soldering.evaluate(Attempt)` — чистая функция (никакого Bukkit), её же
прогоняет `selftest` (строка «пайка: 10° — …, 30° — холодная пайка,
90° — заготовок ×N + припой + флюс; ванильного рецепта светодиода нет: true»).

### 5b. Станки

`Recipes.DEFS` ⇄ `tools/gen_pack.py::RECIPES` — **зеркало**: первое регистрирует
рецепт на сервере, второе кладёт его в датапак (иначе JEI покажет одно, а
соберётся другое). Формат: `Shaped(String[] pattern, map("B", Material.X, …))`
или `Shapeless(List.of(...))`; `map()` принимает по одному символу.
Ванильные `Material` — единственное, что может быть там ингредиентом.

Станки (`SolderGui`, `MetalGui`) работают поверх: игрок держит материалы в
инвентаре, ПКМ по станку, клик по карточке операции. У металлургии таблица
открытая и **без Bukkit** в правилах:

```java
put(CRUCIBLE_ID, new Recipe("ingot_bronze", 1,
        mix("ingot_copper", 2, "ingot_tin", 1),
        mix("ingot_bronze", 1, "slag", 1),
        "бронза — 88% меди и 12% олова; …"));
```

`Metallurgy.missing(Recipe, ToIntFunction<String>)` — та же чистая функция для
GUI, для `selftest` и для офлайн-теста; «списать/выдать/звук» —
`Metallurgy.craft`.

### 5c. Витрины и «пропущено N»

`Recipes.register()` = `unregisterAll()` + обычные рецепты + витрины +
`registerSmelting()`. Витрина (`isDisplayOnly`) показывается в JEI, но
собирается отказом: `Events.onCraftDisplay` слушает `CraftItemEvent` и
отменяет её с подсказкой «это паяют». Плавку руды делает
`FurnaceRecipe` + `ExactChoice` (наш предмет = ванильный полублок, поэтому
`Ingredient` по материалу не годится; `SmokingRecipe` — интерфейс, его
регистрировать нельзя). Счётчик в логе: `зарегистрировано рецептов: 35
(пайка: 61 витрина для JEI, пропущено 7, плавка 3)` — «пропущено» это id без
ванильного крафта (слитки, сплавы, шлак, эмальпровод): их делают станки, и
это норма; но если там оказался id, который **должен** крафтиться, ты
забыл строку в `Recipes.DEFS` + `RECIPES`.

## 6. Каталог, подсказки, команды

* `CatalogGui.WHAT` — текст на **kind**, `WHAT_ID` — на конкретный id
  (`raw_tin_chunk`, `geoprobe`, `wire_stripper`…). `selftest` считает
  `CatalogGui.whatIs(d).isEmpty()` по всему реестру и печатает
  `каталог: 100 предметов, описаний не хватает у 0`. Новая деталь без
  описания = FAIL, и это самая частая незакрытая деталь.
* `Items.componentItem` формирует подсказку предмета: `def.nominal()`
  (номиналы — автоматически из электрики), `kind`, строку «Паяется на
  паяльном столе» + `Soldering.solderHint`, и разное поведение по kind
  (`TOOL` — «ПКМ по печи, прогреть жало»; `STATION` — «ПКМ — открыть
  пайку/станок`; остальные — «ПКМ поставить, Shift+ПКМ повернуть»).
* `/elec show` — GUI каталога; `/elec info` — сводка; `/elec recipe` — что
  где собирается; `/elec give <id> [n]` — выдать (право `electronics.give`);
  `/elec list [фильтр]`, `/elec veins [чанков]`, `/elec solder`,
  `/elec schematic`, `/elec reload`, `/elec selftest`. Табы — в
  `onTabComplete` в конце `ElecCommand`.

Если деталь меняет поведение мира (как геозонд и руды), добавь ключи в
`Config.java` + `config.yml` ( defaults из ресурсов!), примени их в
`reloadAll()` — иначе `/elec reload` будет жить старой конфигурацией.

## 7. Тесты: офлайн и на сервере

**Офлайн** (`bash tools/run_tests.sh`) — компилирует `javac`-ом и гоняет
`tools/Test*.java`: `TestMna` (решатель), `TestTopology` (узел = пара блоков +
расчёт), `TestCoupled` (связанные цепи), `TestDeposits` (недра),
`TestFirmware` (компилятор прошивки), `TestScope` (трасса: измерение, триггер,
растр 40×16 и упаковка в брайль). Секрет в том, что
`shared`-логика этих классов (**`Deposits`, `Firmware`**) намеренно
**не знает про Bukkit** — поэтому её можно тестировать без spigot-api. Если
твоя логика вбирает `Player`/`ItemStack`, тест офлайн не напишешь: либо вынеси
чистое ядро (как `Metallurgy.missing`), либо оставь проверку `selftest`-у.

**`/elec selftest`** (24 строки PASS) строит настоящие цепи в листе-редакторе
(`SchematicGui.forId(plugin, uuid)`, `paintLoop`, `paintRegulator`,
`paintMcu`), считает, сверяет с «бумажной» физикой и печатает числа. Пиши
утверждение так, чтобы в тексте строки были измеренные значения — иначе
проверка ничего не доказывает. Проверенные этим способом ловушки: `veinOf`
вылезал за Y-пояс (офлайн-тест этого не видел), «40 мА/нога» у МК, 8 мВ на
шунте.

Если у детали есть своя сущность в мире (экран, стрелка, подпись),
офлайн-тест её не увидит: `TextDisplay`/`ItemDisplay` проверяй прогоном в мире —
поставить деталь через `Circuit.put`, покрутить рендерер (`renderer().tick()`,
лучше трижды: у экрана есть свой `refresh-ticks`) и найти сущность рядом
(`world.getNearbyEntities`). Ровно так в selftest устроена строка «живой экран
осциллографа»; она же и поймала баг, из-за которого трасса жила бы только после
клика: `refreshScopes()` стоял после `if (pending.isEmpty()) return`.

**Живой прогон** (Paper 1.21.11 build 132, `~/srv`):

```bash
cd ~/electronics/plugin && mvn -q -B -o package
cp -f target/Electronics-1.0.0.jar ~/srv/plugins/
cd ~/srv && pkill -x java; sleep 3; rm -f /tmp/mc.in; mkfifo /tmp/mc.in
(setsid java -Xms512M -Xmx1024M -Dstdout.encoding=UTF-8 -jar paper.jar --nogui \
   <> /tmp/mc.in > mcNN.log 2>&1 &)
# ждём «Done (», потом:
printf "elec selftest\n" > /tmp/mc.in; sleep 35
grep -c FAIL mcNN.log          # должно быть 0; grep -c вернёт код 1 — это успех
```

`grep -c FAIL` с кодом выхода 1 — это не ошибка консоли, а «совпадений нет».

**Проверки пака** (все три вызываются и из `run_tests.sh`, и из `publish.sh`):
`tools/check_pack_refs.py` (каждая пара «id × состояние» имеет модель и
текстуру: `OK: все 100×6 ссылок … разрешается`), `tools/catalog.py`
(генерирует `docs/blocks.md`), `tools/sheets.py` + `tools/preview.py`
(листы `release/textures/sheet-*.png` и `preview.png`).

## 8. Сборка, публикация, пуш

```bash
bash tools/publish.sh      # пак + датапак + превью + листы + jar → release/, sha1sums.txt
git add -A && git commit
bash tools/push.sh v1.3.2  # main (+ тег, релиз и ассеты, если передан тег)
```

* Имя jar **зафиксировано**: `Electronics-1.0.0.jar` (меняется только содержимое —
  иначе надо править `plugin.yml`/доки/скрипты и можно рассинхронизировать `srv/`).
* Воспроизводимость: `project.build.outputTimestamp` в `pom.xml`, поэтому jar CI
  побайтово равен локальному; в `release/sha1sums.txt` есть смысл. **ZIP-и
  побайтово не воспроизводимы** (порядок/метки времени) — сравнивай по
  хешам содержимого по элементам, а не весь архив.
* CI (`.github/workflows/build.yml`): `permissions` только на уровне **job**
  (`contents: write`) — на уровне шага GitHub объявляет весь файл
  «Invalid workflow file», и ран падает за 0 секунд. Шаг релиза идемпотентен
  (`gh release create … || gh release upload … --clobber`), потому что
  `tools/release.sh` часто создаёт релиз раньше CI.
* Список ассетов релиза в `build.yml` **перечислен руками**: если листов стало
  9 — добавь `sheet-09.png`, иначе шаг упадёт.
* Токен: `~/.secrets/github.env` (`GH_LOGIN`, `GH_REPO`, `GH_TOKEN`) — файл
  лежит **вне** репозитория, поэтому не может ни закоммититься, ни уехать в
  пуш. `tools/push.sh`/`tools/release.sh` берут его оттуда, если
  `GITHUB_TOKEN` не задан. PAT нужен: `Contents: Read and write`, плюс
  `Workflows: Read and write`, если коммит трогает `.github/workflows/`
  (иначе GitHub отвергает весь пуш, а не только файл). Логи ранов через API
  читаются только с `Actions: read`; без них — смотри список
  `/actions/runs` и текст ошибки в UI.
* Снимки песочницы **не сохраняют** `build/`, `target/`, `.m2`, а `.git` иногда
  откатывают (дваждыHEAD уезжал на доисторический коммит и возвращал битый
  `build.yml`). Страховка: `git bundle create ~/backups/electronics-main.bundle
  --all` после каждой выложенной версии; восстановление —
  `git fetch ~/backups/electronics-main.bundle +refs/heads/main:refs/remotes/origin/main
  +refs/tags/*:refs/tags/*` и `git reset --mixed <sha>`.

| Симптом | Причина / решение |
|---|---|
| `cannot find symbol Material.SULPHUR` | в 1.21.11 нет — `Material.GUNPOWDER` |
| `SmokingRecipe` не регистрируется | это интерфейс; бери `FurnaceRecipe` |

| «рецепт не задан для …» в генераторе пака | id ни ванильный, ни спаечный → заведи рецепт или добавь в `BY_DESIGN` |
| деталь есть, но стакается/не стакается не так | `stack` в реестре; `solid` — для станков |
| предмет «невидимка» (белый куб) | нет `items/<id>.json`/модели: пак не перегенерирован или срез индексов съехал из-за вставки в середину реестра |

| ток детали читается 0 при явном КЗ | нога объединилась с GND этой же детали (`a == b`), ветви нет — считай явно |
| `prev` пуст на проходе 0 → ложное срабатывание лимита | засевай узел номиналом (`vccSeed`), как у стабилизатора |
| selftest «нет описания» | забыл `CatalogGui.WHAT/WHAT_ID` |
| GUI-поле ввода не работает | в chest-GUI поля ввода нет: многострочный текст — только книга для записи |
| `variable x is already defined in method selftest` | в ~460-строчном методе локальные имена сталкиваются; грепни перед вставкой |
| Python-патч «AssertionError» на якорь | русский текст в исходнике склеен иначе; сначала `grep -n`, лучше править по номерам строк |
| `heredoc` внутри составной команды проглотил хвост скрипта | не `<<'PY'` в составе команды, а `write_file` + `python3 /tmp/x.py` |
| HEAD «не там», `build.yml` снова битый | откат снимка: восстанавливай из bundle (§8) |
| «мотор горит» на разгоне, а сгореть должен от упора | `protect()` у MOTOR сравнивает **мгновенную** мощность; копи секунды перегрузки (§4bis.6) |
| ток привода ~0 мкА при вращающемся валу | `speedPrev` передали в об/с вместо доли паспортных оборотов; ЭДС получилась больше сети (§4bis.3) |
| механизм стоит, подсказка «тяги не хватает» | под колесом камень, а не рельс: μ 0.35 против 0.005 (§4bis.5) |
| после `/elec rig place` цепь пропала на втором метре пути | каретка уехала с подводящего провода; для демо либо питай вдоль всего пути, либо `carriage-move: false` |
| CI «ран падает за 0 секунд» | невалидный YAML workflow (например `permissions` на шаге) |
| пуш отвергнут целиком | PAT без `Workflows: Read and write` при изменении workflow |
